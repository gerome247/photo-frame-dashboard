# PF1007L with "OS-PF1009" firmware 20260417 (unit E)

Two units (E and F, same firmware), macOS (Apple silicon), 2026-10-11/12. Both are rooted and running
the kiosk. The firmware string differs from every unit in
[pf1007l-start-here.md](pf1007l-start-here.md): it ends in `OS-PF1009.0.20260417` instead of
`321-OS-AIMOR.0.2026xxxx`, `V10-1680.0.2026xxxx` or `FL-AIMOR-OS.0.2026xxxx`. The board prefix
(`A33-1001-D1024-PF1007L`) is the same. Observations and guesses are kept separate below.

## Observations

### Cable-only routes that did not give ADB

Tried before buying an SD card. None changed anything on the frame.

| Attempt | Result |
| --- | --- |
| Tap the firmware/build line in the About screen 7 times | Nothing. No developer-options toast |
| Catch the `1f3a:efe8` window at power-up with a `sunxi-fel version` loop | The device is present for about 3 s. Every query failed: `usb_bulk_recv() ERROR -1: Input/Output Error`, then `Allwinner USB FEL device not found!`. Reproduced 3 times. Matches the Boot ROM FEL being unreachable without the stub card |
| Hold the button while connecting power | Opens a vendor (AiMOR-style) menu, not Android recovery. No USB change: still `1f3a:1000`, mass storage only, no ADB interface |

### USB data

- At least one of the owner's USB-A to USB-C cables carried power only (screen on, nothing on the
  bus). Testing each cable with a phone against `ioreg -p IOUSB` was the quickest way to find a
  data cable.
- Plugging the frame into the hub made the hub's USB 3 half (and the card reader on it) drop and
  re-enumerate at the same moment, at least once. That looks like an inrush dip on a bus-powered
  hub (guess, not measured). Data still worked after re-seating the plug.

### FEL stub card on a blank card

The owner's new 32 GB card had no partition table, so `fel-card-macos.py backup` refuses it ("GPT or
empty layout not supported"). An MBR with one FAT32 partition starting at sector 8192 fixed it:

**These commands erase the whole disk you name, with no confirmation.** First run
`diskutil info diskN` and check that Device Location is External, Removable Media is Removable,
Protocol is USB or Secure Digital, and Disk Size is your card's size. A wrong disk number erases
that disk. Disk Utility (Erase, MS-DOS (FAT), Master Boot Record) is a safer way to get an MBR card,
but its first partition may start before sector 8192; `fel-card-macos.py backup` tells you.

```sh
echo "8192,$((SECTORS - 8192)),0x0C,-" | sudo fdisk -y -r /dev/diskN   # SECTORS = Disk Size / 512
sudo newfs_msdos -F 32 -v FELCARD /dev/rdiskNs1
```

`fdisk` prints `could not open MBR file /usr/standalone/i386/boot0` on Apple silicon; that is harmless
and it still exits 0. Then `backup` and `write` worked as documented, and FEL came up with a dark
screen.

### Route U with the low-power U-Boot

The repo build was not tried on this unit. Because #16, #17, #18 and #19 all saw `ums` drops on the
30,777,344-sector eMMC, this unit went straight to #16's changes on top of `pf1007l-uboot.patch`:
`CONFIG_SUNXI_NO_PMIC=y`, `CONFIG_SYS_CLK_FREQ=408000000`, eMMC 4-bit at 26 MHz, no CTRL+C abort, and
START STOP UNIT ignored. Built DTB: `bus-width = <0x04>`, `max-frequency = <0x18cba80>`. SPL code ends
at 0x3ee6 (eGON length 0x4000). `build-uboot.sh`'s SPL check would have stopped on the 0xFF padding, as
#16 noted.

**These U-Boot changes are not in this repository's build scripts yet.** They came from issue #16 and
were applied by hand, with the SPL check bypassed. See the U-Boot settings table in
[pf1007l-start-here.md](pf1007l-start-here.md#u-boot-settings-that-fixed-ums-problems).

- `ums` exposed "UMS disk 1", 15,758,000,128 bytes, Media Read-Only: Yes.
- Through the bus-powered hub, the frame was still on USB minutes after "Starting U-Boot", past the
  45-50 s reset reported in #19. The read-only `ums` later stayed up for over an hour while idle.
- Attempt 1, plain `emmc-macos.py backup` through the bus-powered hub: pass 1 ran at 8.2-8.4 MB/s for
  about 16 minutes, then failed at 50% (7,918,845,952 bytes) with `OSError: [Errno 6] Device not
  configured` in `chunks()`. The frame was gone from USB entirely, not back in FEL, while the hub's
  other devices stayed. That matches #16, where the drops ended only on a direct port.
- No direct port was available, so a resumable mode was added to `emmc-macos.py`
  (`backup-resume` / `verify-resume`, and `verify-original-resume` for the undo): 1 GiB segments,
  progress saved after each one. Each segment is read twice from the disk and once back from the image
  file, and all three must match. On resume, the disk must still be the same frame. (In this PR that
  check compared only the first 4 MiB, which is identical on every unit with this firmware. It now also
  compares the start of the user-data partition, which is unique per unit.)
  After a drop: power-cycle into FEL, load the same U-Boot, rerun the same command.
- Result: all 15 segments done, each read twice and matched; full image 15,758,000,128 bytes; gzip
  372 MB with readback verified. A whole-image hash check of the image against its recorded SHA-256
  matched again before T6.

### Boot patch (offline)

`boot-patch.py backups/a33-emmc-full.img 172032` passed all its checks on this untested image:
one cpio file changed (`init.sun8i.usb.rc`, the documented action), 22 header bytes changed, all in
16-19 (ramdisk size) and 576-595 (image ID), nothing after the slot changed. The recompressed ramdisk
is 5,632,463 B, 28,209 B under the slot. An independent re-parse confirmed the same.

| | Value |
| --- | --- |
| Write ranges | ramdisk `[192004, 203060)` (11,056 sectors), header `[172032, 172034)`, the same as on the tested units |
| Payload CRC-32 | orig header `7e2622e5`, new header `0d28ecec`, orig ramdisk `795e262b`, new ramdisk `dad5bc75` |
| Guards in `write-boot.scr` | `crc32 -v` on all four payloads, then `cmp.b` of the eMMC's current header and ramdisk slot with the originals |

The low-power build already has `MMC_WRITE`, `CMD_CRC32` + `CRC32_VERIFY`, `cmp.b` and the hush
parser, so the same build serves for the write; only `ums` writes are patched out.

### Write, verify and root (unit E)

- The guarded write ran from FEL with the low-power U-Boot (payloads at 0x50000000-0x53000000,
  `write-boot.scr` at 0x43100000). The disk coming back as "UMS disk 0" does not by itself show that
  the guard allowed the write, so the two ranges were read back first: header `63de6d6e...`, ramdisk
  `6aa00e39...` (SHA-256 prefixes of `new-header.bin` / `new-ramdisk.bin`; the refused case would read
  `29dd0ff6...` / `be18d740...`).
- `verify-resume` through the same bus-powered hub, 15 segments with no drop: "Verified: the eMMC
  equals the backup plus exactly the planned boot patch."
- Card out, normal boot: `adb devices` shows the frame as `device`, `adb -d shell id` gives
  `uid=0(root)`, `ro.adb.secure=0`, so there is no authorization prompt (and no SystemUI to show one).
- **The first rooted boot rejoined the saved Wi-Fi network silently**, the same as #27 reports. The
  frame had been put on Wi-Fi earlier for the T3b test. `svc wifi disable` went first, before T8.
  Forgetting the network before the patch, as #27 suggests, would avoid that window.

### T8, WebView 106 and kiosk

- T8 as documented: the in-memory `vendor_block` chain, the kiosk installed as a Home app, then
  `pm disable` for `com.efercro.os.aimor`, `com.yhk.qeota` and `com.DeviceTest`, plus
  `com.android.gl2jni` (`tomas.apk`: one activity, storage and wake-lock permissions only, no services
  or receivers), `com.svox.pico` and `jp.co.omronsoft.openwnn`. All six reached `enabled="2"` in
  `package-restrictions.xml` within seconds, survived a reboot, and nothing listened or connected on
  7806 afterwards. The other 28 packages are core Android and were left alone.
- Wi-Fi had switched itself back on between `svc wifi disable` and the AiMOR disable (guess: AiMOR
  re-enabled it). With AiMOR disabled it stayed harmless.
- WebView 106 swap as in section 6 of the PF1007L guide: `versionName=106.0.5249.126` after reboot,
  no `dlopen failed`; the kiosk as Home starts at boot.
- Shipped settings worth changing: automatic brightness was on (`screen_brightness=140`,
  `/sys/class/disp/disp/attr/lcdbl` 97 of 255; `screen_brightness_mode 0` + `255` gives 255), and the
  time zone was `America/New_York`.
- WebView 106 on this GPU: one big semi-transparent layer whose `opacity` was animated (a twinkling
  star field drawn into a canvas image) rendered as an opaque olive band on unit E. The same image without the animation drew correctly. A full-screen animated
  background on top of three camera snapshot tiles also visibly stuttered. Small UI animations were
  fine.

### Second unit (F): same firmware, patched without a second full backup

**Not recommended.** This skipped the repository's backup rule. It worked here, but F's own data
and any differences outside the boot region had no backup.

- `ro.build.display.id` `astar_m86_8723cs-eng 6.0.1 MOB30R 20260417 test-keys.1`, the same eMMC size.
  FEL with the same stub card and the same low-power U-Boot.
- The boot region the patch touches (sectors 172032 to 203060) read back **byte-identical to unit
  E's original** (same SHA-256 `3f0dc9d5448e965b...` as above). Because of that, the owner chose not to
  take a 65-minute full backup of F: E's backup holds the exact original bytes for every written
  sector, so it serves as F's undo for the patch. `write-boot.scr` checks the original bytes itself
  in any case. F's own user data was not backed up.
- Same guarded write, same read-back (`63de6d6e` / `6aa00e39`), root ADB on the first boot. Like E,
  it came up on its saved Wi-Fi.
- **USB data on F kept dropping every 10-60 s** with two cables that worked fine for E. Flipping the
  USB-C plug 180 degrees at the frame end gave a stable link (guess: one orientation has a poor data
  contact; E also lost data once and came back after re-seating).
- Over that flaky link, a read-back check with `adb exec-out cat <file> | shasum` of the 55 MB
  WebView APK came back truncated and failed even though the file was correct. Checksumming on the
  frame (`md5sum` and `sha1sum` are in `/system/bin`) and comparing with the host avoids that.
- A detached `nohup sh -c "mv ... && mv ..." &` for the WebView swap never ran: the job was killed
  when the `adb shell` session closed. Running the two renames in the foreground with
  `sh -c 'trap "" HUP; ...'` worked.

## Guesses

- `OS-PF1009` looks like a product/branding variant (`ro.es_frame.product=PF1009`) of the same AEEZO
  `astar_m86_8723cs` April build line, not a different board: same fingerprint pattern, partition
  layout, boot image size, ramdisk slot, vendor apps and AiMOR version. The boot image differs from
  #17's 20260410 image in content, not layout.
- The 2016 security patch level and `test-keys` mean the root and AiMOR exposure described in
  [aimor-remote-root-shell.md](aimor-remote-root-shell.md) applies here unchanged.
